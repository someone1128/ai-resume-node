# Java / Node 性能基线

更新时间：2026-09-22

迁移目标是减少 Snowy 平台无关模块、启动依赖和常驻内存，但在没有相同机器、相同数据库、相同请求集合和相同并发量的情况下，不给出内存或性能节省百分比承诺。

## 当前 Node 基线

- 运行时：Node.js 22+；
- 服务：Fastify 5 + TypeScript 编译产物；
- 冷启动：本地编译产物可以启动并返回 `GET /health` 的 `200`；
- 数据库未就绪时：`GET /ready` 返回 `503`，不会误报可用；
- 生产依赖审计：Node 当前无已知生产依赖漏洞（0 low、0 moderate、0 high、0 critical）；
- 业务测试：Node 40/40 通过。

冷启动和内存的正式数字必须在与 Java 服务相同的主机、JVM 参数、数据库连接数和环境变量下采集。开发模式的 `tsx watch`、构建缓存和浏览器开发服务不纳入比较。

## 切换前测量方法

1. 为 Java 和 Node 分别创建干净进程，固定同一台机器和同一份环境配置。
2. 记录进程启动到健康检查成功的时间，重复至少 10 次，报告中位数和 P95。
3. 服务完全空闲 10 分钟后记录常驻集（RSS）和堆内存。
4. 使用同一组只读请求和隔离测试账号，逐步压测 1、10、50 个并发，记录吞吐、P95、错误率、RSS 峰值和数据库连接数。
5. 单独测量 AI、COS、微信支付 mock 和 WebSocket，不把外部服务等待时间误算成 Node 或 Java 本身的计算性能。
6. 记录 GC、事件循环延迟、数据库连接池等待和超时；任何一项异常都阻止直接切换。

## 目前不能推导的结论

- 不能仅凭 jar 包数量推导线上内存节省；真正的占用取决于 JVM 堆、线程、连接池、缓存和请求负载。
- Node 通常会减少空闲线程和基础框架常驻开销，但 CPU 密集的文档解析、图片处理和 AI 外部等待仍需独立测量。
- Java 和 Node 的正式对比需要预发布压测结果；在此之前只把 Node 的冷启动、健康检查和自动化测试结果作为工程基线。

## 可重复的只读基线

Node 提供 `pnpm bench:health`，只对 `/health` 或 `/ready` 发送 GET 请求，不创建或修改业务数据。例如：

```powershell
$env:BENCH_URL = 'http://127.0.0.1:8823/health'
$env:BENCH_REQUESTS = '1000'
$env:BENCH_CONCURRENCY = '50'
pnpm bench:health
```

输出包含成功率、状态码分布、p50/p95/p99、最大延迟和压测进程 RSS。正式 Java/Node 对比仍需在同一预发布机器、同一数据库和同一连接池配置下执行，不能用本地单端点数据替代。
